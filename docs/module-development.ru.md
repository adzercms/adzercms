# Свой модуль

[English](module-development.md) | Русский

Модуль — это пакет Composer с бандлом Symfony. Он зависит от контрактов `adzercms/contracts`, а не от реализации ядра.

## Пакет

Модуль заводится в каталоге `modules/` экземпляра:

```sh
composer create-project adzercms/module-skeleton modules/pigeon --stability=dev --no-install
composer require acme/pigeon:@dev
```

`create-project` спрашивает имя пакета, namespace, класс бандла и что делает модуль — по-английски и по-русски. Новый пакет — модуль функции с бандлом, тестом и CI с [проверкой модуля](#проверка-модуля). Его `composer.json` выглядит так:

```json
{
    "name": "acme/pigeon",
    "type": "adzercms-module",
    "description": "SMS through a pigeon post",
    "license": "MIT",
    "require": {
        "adzercms/contracts": "^1.0",
        "symfony/dependency-injection": "7.4.*",
        "symfony/translation": "7.4.*"
    },
    "provide": {
        "adzercms/sms-implementation": "1.0.0"
    },
    "autoload": {
        "psr-4": {"Acme\\Pigeon\\": "src/"}
    },
    "extra": {
        "adzercms": {
            "bundle": "Acme\\Pigeon\\PigeonBundle",
            "description": {"ru": "SMS голубиной почтой"}
        }
    }
}
```

`extra.adzercms.bundle` указывает класс бандла. Имя этого класса без `Bundle` — ключ модуля, и среди установленных модулей он должен быть уникальным. Если модуль требует пакет другого модуля, тот модуль тоже должен быть включён.

`description` по-английски говорит, что делает модуль, а `extra.adzercms.description` переводит это на остальные языки движка. Раздел модулей админки показывает описание на языке читателя, в том числе у ещё не установленных пакетов. `vendor/bin/adzercms-check` отклоняет модуль без описания или без одного из его переводов.

Модуль нужного вида требуют не по имени пакета, а через виртуальный пакет вида `adzercms/<ключ вида>-implementation`. Каждый модуль вида указывает его в `provide` с версией движка, контракты которой он реализует; модуль вида без этой записи останавливает сборку. Тогда Composer поставит требующий модуль только вместе с каким-то модулем нужного вида, а экземпляр соберётся, только если такой модуль включён. Модулю со страницами нужна тема: `"adzercms/theme-implementation": "^1.0"`. Модули, которые нужны только тестам, такие как админка, указываются в `require-dev`: набор тестов модуля включит их сам.

Пакет требует каждый пакет и каждое расширение PHP, чьи классы, функции или константы использует его код. Зависимость, которая пришла через другой пакет, сломается, как только тот пакет от неё откажется. `vendor/bin/adzercms-check` с помощью [composer-dependency-analyser](https://github.com/shipmonk-rnd/composer-dependency-analyser) ищет в PHP-файлах пакета вне `tests/` недостающие, лишние и записанные не в тот раздел требования и не пропускает их. Если зависимость нужна только конфигурации бандла или шаблонам, исключите её из лишних в `composer-dependency-analyser.php` в корне пакета — это конфигурация анализатора. Пакет, которым модуль пользуется, только когда тот установлен, указывается в `suggest`.

## Ссылки на админку и кабинет

Ссылки на страницы админки и кабинета строятся через входы: функции Twig `admin('user', {id: id})` и `cabinet('profile')`, а в коде — `AdzerCMS\Core\Ui\Entries::url()` с `AdminEntry` или `CabinetEntry`. Если модуля этого вида нет, вход возвращает `null`, и страница просто не выводит ссылку.

## Страницы админки и кабинета

Модуль функции описывает свои части админки и кабинета сервисами с интерфейсами `AdzerCMS\Contracts\Ui`, а включённый модуль админки или кабинета рисует их в своём каркасе. Такие сервисы регистрируются автоконфигурацией.

- `Menu` — `items()` отдаёт пункты меню для `Area`: админки или кабинета. Пункт `MenuItem` содержит маршрут, подпись, вес, связанные маршруты (на них пункт остаётся активным), группу, счётчик, признак диалога, а для нижней панели кабинета — значок из набора темы и короткую подпись. Пункты с одинаковой подписью группы попадают в одну группу; группа записи кабинета, где профиль и выход, подписана ключом ядра `core.menu.record`.
- `Tabs` — вкладки страницы по её ключу: `Tabs::ADMIN_DASHBOARD`, `Tabs::ADMIN_USER` или `Tabs::CABINET_HOME`. `tabs()` отдаёт вкладки `Tab` с ключом, подписью, весом и необязательным числом, а `tab()` строит шаблон и контекст только активной вкладки.
- `Fragment` — фрагмент чужой страницы в заданном месте: `Fragment::HEAD`, `TOP` (шапка и навигация раскладки `top` вместо панельных), `HEADER`, `CABINET_HOME`, `CABINET_PROFILE` (профиль под контактами), `ADMIN_DASHBOARD`, `ADMIN_DASHBOARD_ACTIONS`, `ADMIN_USER`, `END` (конец тела страницы — окна модуля поверх любой страницы). `null` оставляет место пустым.
- `Columns` — колонки модуля в чужом списке, `Columns::ADMIN_USERS`. `cells()` отдаёт значения `Cell` для всех строк страницы одним вызовом, а `search()` — строки, которые модуль нашёл по своим полям. По таким колонкам список не сортируется.
- `ContentSource` — дополнительные источники для директив `form-action`, `script-src`, `connect-src`, `frame-src` и `style-src` в Content Security Policy.

Метка состояния — `Badge::good()`, `warn()`, `bad()` или `idle()`. Если действие невозможно, оно отказывает через `AdzerCMS\Contracts\Refusal` с причиной и маршрутом, где её можно устранить.

## Бандл

Бандл наследует `AdzerCMS\Contracts\Module\Module`: `kind()` называет вид модуля, а `kinds()` перечисляет виды, которые модуль объявляет сам (по умолчанию — ни одного). Symfony Flex не добавляет такой бандл в `config/bundles.php`: какие модули включены, экземпляр задаёт в своём окружении.

```php
namespace Acme\Pigeon;

use AdzerCMS\Contracts\Module\CoreKind;
use AdzerCMS\Contracts\Module\Kind;
use AdzerCMS\Contracts\Module\Module;
use Symfony\Component\DependencyInjection\ContainerBuilder;
use Symfony\Component\DependencyInjection\Loader\Configurator\ContainerConfigurator;

final class PigeonBundle extends Module
{
    public static function kind(): Kind
    {
        return CoreKind::Sms;
    }

    public function loadExtension(array $config, ContainerConfigurator $container, ContainerBuilder $builder): void
    {
        $container->services()->set(PigeonGateway::class)->autowire()->autoconfigure();
    }
}
```

Модуль функции возвращает `CoreKind::Feature`. Если у него есть свои заменяемые части, это его виды: enum с контрактом `AdzerCMS\Contracts\Module\Kind`. У каждого вида есть ключ, ключ переменной окружения и признак «один модуль или список».

## Модуль вида со списком

Шлюзы SMS, капчи, сервисы входа и боты реализуют контракт своего вида. Этот контракт расширяет `AdzerCMS\Contracts\Module\Switchable`: модуль объявляет поля для ключей доступа, ядро хранит их в настройках `<вид>.<модуль>.<поле>` рядом с переключателем `enabled` и передаёт значения в каждый вызов.

```php
namespace Acme\Pigeon;

use AdzerCMS\Contracts\Module\Credentials;
use AdzerCMS\Contracts\Notice\SmsFailed;
use AdzerCMS\Contracts\Notice\SmsGateway;
use AdzerCMS\Contracts\Setting\Field;
use AdzerCMS\Contracts\Setting\Type;

use function Symfony\Component\Translation\t;

final class PigeonGateway implements SmsGateway
{
    public function credentials(): array
    {
        return [new Field('token', t('pigeon.token'), Type::Secret, required: true)];
    }

    public function send(Credentials $credentials, string $phone, string $text): void
    {
        // вызываем провайдера с $credentials->get('token'), при отказе бросаем SmsFailed
    }

    public function contract(Credentials $credentials): array
    {
        return [];
    }
}
```

Сервис должен лежать в namespace своего бандла: по нему ядро понимает, какому модулю сервис принадлежит.

## Канал уведомлений

Модуль функции может добавить свой канал уведомлений сервисом `AdzerCMS\Core\Notice\Channel`; сервис регистрируется автоконфигурацией. Канал встаёт сразу после ботов и перед телефоном и почтой: в порядке доставки каждого уведомления, в переключателях кабинета и в журнале. Если каналу некуда доставить уведомление пользователю, `missing()` подсказывает, что сделать, чтобы канал заработал. Подключение канала выводится фрагментом `Fragment` в месте `Fragment::CABINET_PROFILE`, туда и ведёт `missing()`.

## Сообщения ботам

Модуль функции получает то, что люди пишут ботам, через сервис `AdzerCMS\Contracts\Notice\BotListener`; сервис регистрируется автоконфигурацией. `heard()` получает ключ модуля бота, его сервис входа и сообщение `Incoming` и возвращает ответ отправителю или `null`, если сообщение не для этого модуля. Слушатели опрашиваются по очереди, первыми идут коды подключения ядра; первый же ответ уходит отправителю, и опрос заканчивается. `AdzerCMS\Core\Notice\BotLink::code()` выдаёт код из алфавита ядра, а `hash()` — хеш введённого кода для хранения.

## Слушатели входа

Модуль функции, который ждёт входа через сервис, может забрать профиль сервиса входа вместо того, чтобы пользователь вошёл на сайт. Для этого служит сервис `AdzerCMS\Contracts\Login\LoginListener`, он регистрируется автоконфигурацией. `entered()` получает ключ сервиса входа, его `Profile` и запрос возврата и возвращает ответ или `null`, если вход не для этого модуля. Первый ответ завершает возврат: никто не входит, и ничего не привязывается.

## Сервис входа

Сервис входа реализует `AdzerCMS\Contracts\Login\LoginService`. `authorization()` возвращает адрес авторизации с client id и scope, `pkce: false` для сервиса без PKCE, `nonce: true` для сервиса, который проверяет `nonce` в своём `id_token`, и дополнительные параметры запроса. Ядро добавляет `state`, redirect URI и одноразовый секрет: `code_challenge` для PKCE либо значение `nonce` как есть.

`profile()` получает возврат как `Callback`: код, `state`, секрет в виде `code_verifier` или ожидаемого `nonce`, redirect URI и любой параметр запроса через `parameter()`. Сервис вызывается через `Exchange`: если ответ не 200, содержит `error` или не пришёл вовсе, бросается `LoginFailed` с причиной. Ответ приходит как `Answer`: `text('user', 'email')` читает поле по цепочке ключей, а отсутствующее, пустое или нескалярное поле даёт `null`. `claims()` принимает `id_token` вместе с адресом JWKS, издателем и client id, проверяет подпись ключами сервиса, `iss`, `aud` и срок действия и возвращает claims как `Answer`. `Client::basic()` собирает заголовок `Authorization` из идентификатора и секрета приложения. Свои отказы модуль бросает как `LoginFailed`, а в итоге отдаёт `Profile` с id профиля в сервисе. Поля идентификатора и секрета приложения — `AdzerCMS\Contracts\Login\Client::Id->field()` и `Client::Secret->field()` с подписями ядра. Значок сервиса — его официальный логотип в файле `public/icon.svg` пакета.

В настройках приложения на стороне сервиса укажите redirect URI `https://<хост>/login/<ключ модуля в нижнем регистре>/callback`. Вход начинается с адреса `/login/<ключ модуля в нижнем регистре>`.

## Раскладка пакета

- `src/Entity/` — сущности Doctrine на атрибутах; имена таблиц начинаются с имени модуля
- `migrations/` — миграции в namespace `<namespace бандла>\Migrations`
- `src/Controller/` — контроллеры с атрибутами маршрутов
- `templates/` — шаблоны Twig в пространстве `@<Модуль>`
- `translations/` — каталоги XLIFF `messages+intl-icu.<язык>.xlf`; ключи начинаются с имени модуля, английский каталог обязателен, набор ключей во всех языках одинаковый, а каждый ключ кода и шаблонов есть в английском каталоге модуля или модуля, который он требует
- `tests/` — тесты PHPUnit

Сущности, миграции и маршруты включённого модуля ядро подключает само.

Даты показывайте на языке читателя через переводчик, а не фильтром Twig `date`. Внутри фразы дата — аргумент ICU со скелетом, например `{until, date, ::yMMdd}`. Отдельная дата берёт ключ ядра: `core.moment.day`, `core.moment.time`, `core.moment.day_time` или `core.moment.month` с аргументом `at`. Экземпляр меняет вид дат, перекрывая эти ключи своим каталогом.

Суммы выводятся со знаком рубля на языке читателя: фильтр `money` даёт целые рубли, `precise` добавляет копейки, если они есть. В коде `AdzerCMS\Core\Ui\Money::rubles()` и `precise()` дают переводимую сумму для аргумента фразы. Не дописывайте знак сами: подпись поля или колонки называет единицу своей фразой.

Кнопки общих действий берут ключи ядра: `core.action.close`, `core.action.save`, `core.action.edit`, `core.action.drop` и `core.action.to_list` на странице записи. Действие над конкретным объектом и подпись поля берут ключи вашего модуля. Модальное окно начинается с заголовка темы `@Theme/_modal_header.html.twig` с аргументом `title`, в нём же кнопка закрытия. Поле файла — шаблон темы `@Theme/_file.html.twig` с аргументами `name` и `accept`, необязательными `id`, `multiple` и `required`: кнопка говорит на языке страницы, за ней — имена выбранных файлов.

## Тесты

Тесты модуля запускаются в экземпляре, где модуль лежит в `modules/`. Composer читает `autoload-dev` только корневого пакета, поэтому экземпляр сам прописывает namespace тестов модуля и заводит в `phpunit.dist.xml` набор с именем ключа модуля.

```json
"autoload-dev": {
    "psr-4": {"Acme\\Pigeon\\Tests\\": "modules/pigeon/tests/"}
}
```

```xml
<testsuites>
    <testsuite name="Pigeon">
        <directory>modules/pigeon/tests</directory>
    </testsuite>
</testsuites>
```

Набор включает свой модуль, модули, которые он требует, модули из его `require-dev` и по модулю каждого нужного ему вида. Если у модуля есть сущности, добавьте в его набор тест миграций ядра: `<file>vendor/adzercms/core/tests/Schema/MigrationsTest.php</file>`. Пустую тестовую базу данных укажите в `.env.test.local`: она общая для всех наборов, а первый тест прогона удаляет её и накатывает миграции заново.

```sh
composer dump-autoload
bin/phpunit --testsuite Pigeon
vendor/bin/adzercms-check
```

Тест с базой данных наследует `AdzerCMS\Core\Tests\SchemaTestCase`, а ответы внешних сервисов задаются через `AdzerCMS\Core\Tests\HttpAnswers`.

## Проверка модуля

Проверка модуля запускается в экземпляре, где модуль установлен. Она включает модуль так же, как его тестовый набор, и останавливается на первой непройденной проверке:

```sh
bin/php vendor/bin/adzercms-module-check acme/pigeon
```

- `build` — контейнер собирается с модулем, а его сервисы получают аргументы объявленных типов
- `catalogs` — каталоги перевода модуля соответствуют правилам `translations/` выше
- `audit` — `composer audit` не находит уязвимостей у пакетов, которые добавляет экземпляру только этот модуль
- `phpstan` — PHPStan каталога `src/` модуля на уровне движка
- `psalm` — анализ taint каталога `src/` модуля в Psalm с плагином Symfony: данные запроса не попадают в отслеживаемые Psalm приёмники — SQL, команды оболочки, пути файлов и другие. Плагин Symfony считает HTML тело любого `Response`, поэтому ответ простым текстом — `AdzerCMS\Core\Http\TextResponse`
- `boundary` — модуль не переопределяет и не декорирует сервисы других пакетов и не меняет их маршруты, консольные команды и переводы; его миграции создают и меняют только таблицы его собственных сущностей. Схема проверяется на каждом адресе БД из `MODULE_CHECK_DATABASES` через пробел; без переменной — на тестовой БД, пустая переменная схему пропускает
- `theme` — только у темы: в ней есть все шаблоны, функции, фильтры и тесты Twig темы движка `adzercms/theme` и классы оформления, которые берут шаблоны других установленных пакетов `adzercms/*`

Непройденная проверка завершает прогон с кодом выхода 1 и своим именем в последней строке.

В CI репозиторий модуля вызывает задание проверки модуля движка:

```yaml
jobs:
  module-check:
    uses: adzercms/adzercms/.github/workflows/module-check.yml@main
```

Задание создаёт экземпляр из `adzercms/skeleton` со всеми модулями движка и модулем из репозитория и запускает проверку на PostgreSQL, MySQL и MariaDB. Если Composer не может разрешить требования модуля, проверка не проходит как `install`.

Версию, опубликованную на Packagist, движок проверяет так же в течение суток. Прошедшая версия получает отметку «проверен» в каталоге модулей каждого сайта. Каждый коммит проверяется один раз, а отметка остаётся, пока версия опубликована.

## Миграции

```sh
bin/console doctrine:migrations:generate --namespace='Acme\Shop\Migrations'
```

Сгенерированный класс не выполнится, пока вы его не допишете. Таблицы описываются объектами DBAL `Table` и SQL платформы `$this->platform`, а не строками SQL, — тогда модуль работает на MySQL, MariaDB и PostgreSQL. Классы модуля в миграциях не используются.

Применённая миграция запоминается по имени класса. Если модуль сменил namespace или миграция переехала в другой набор, она не выполнится повторно: консоль миграций перенесёт отметку на миграцию с тем же номером версии. Закоммиченную миграцию не меняют: экземпляр, который её уже применил, не выполнит её снова. Поэтому изменение схемы — всегда новая миграция, а правку закоммиченной не пропустит хук `pre-commit`.

## Настройки

Сервис с контрактом `AdzerCMS\Contracts\Setting\Owner` объявляет поля настроек. Ключи начинаются с префикса модуля; если один ключ объявят два владельца, каталог настроек не соберётся. Значения меняются командой `bin/console adzercms:setting`.

В админке поля модуля образуют его вкладку настроек с подписью из фразы `<module>.setting.area`; вкладки модулей идут после вкладок ядра в порядке подписей. Поле с `tab:` из вариантов `AdzerCMS\Contracts\Setting\Tab` попадает во вкладку ядра. `section:` собирает поля под заголовком, а поля без раздела открывают вкладку без заголовка. Подпись помещается в одну строку колонки: название настройки, затем единица через запятую.

## Обновление страниц в реальном времени

Часть страницы, которая меняется без действий пользователя, — живой блок: элемент с `id` и атрибутом `data-live`. Если установлен модуль `realtime`, сервис с контрактом `AdzerCMS\Realtime\LiveEntities` объявляет сущности, изменения которых обновляют живые блоки. `fields()` сопоставляет классу сущности поля, изменения которых учитываются; пустой список означает любое изменение. `owner()` называет пользователя, чьи страницы обновляются, а `staff()` обновляет ещё и страницы операторов. Создание и удаление объявленной сущности учитываются всегда. Модуль указывает `adzercms/realtime` в `suggest` и регистрирует сервис, только если интерфейс существует:

```php
if (interface_exists(LiveEntities::class)) {
    $container->services()->set(LiveShipments::class)->autowire()->autoconfigure();
}
```

Модуль сервера обновлений возвращает `AdzerCMS\Realtime\HubKind::Hub` из `kind()` и реализует `AdzerCMS\Realtime\RealtimeHub`. `client()` указывает его клиент для браузера: ES-модуль в `public/` пакета, который экспортирует `connect(settings, event)`. В `settings` передаются адрес и токен подключения, каналы с токенами подписки и функция `renew(channel)`, которая получает новый токен или `null`, если текущему входу токен не выдан. `event()` вызывается при публикации и при потере истории.

## Каталог для OPOTOPO

Если установлен модуль `opotopo`, модуль функции предлагает свой каталог к продаже на [OPOTOPO](modules.ru.md#продавать-на-opotopo) сервисом с контрактом `AdzerCMS\Opotopo\Catalog`:

- `name()` — имя каталога, уникальное среди модулей; его принимает параметр `--catalog` задания `adzercms:opotopo`
- `mapping()` — какие значения записи становятся полями объявления, категорией OPOTOPO, атрибутами, изображениями, 3D-моделью и вариантами, в формате [клиента на PHP](https://opotopo.com/knowledge/developers/klient-na-php)
- `records()` — позиции каталога, собранные `AdzerCMS\Opotopo\Records::record()` из ключа, который у позиции никогда не меняется, и её значений по путям сопоставления. Значение медиа, которое не адрес `http://` или `https://`, — путь к файлу в каталоге файлов сайта

Модуль указывает `adzercms/opotopo` в `suggest` и регистрирует сервис, только если существует `AdzerCMS\Opotopo\Catalog`, так же, как живой блок.

## Контракты

`adzercms/contracts` следует SemVer: несовместимое изменение контракта выходит только в новой мажорной версии. Виды и события модуля функции — контракты его собственного пакета.
